Stopped setting `HARN_RELEASE_CARGO_TARGET_DIR` in the hosted release workflow. Harn validates every `HARN_`-prefixed environment name at startup and rejects that one, so the first hosted run aborted with `HARN-ENV-001` before the harness read it.

Moved the harness's own environment knobs into the `HARN_EXT_` namespace that Harn reserves for downstream embedders, which fixes that failure as a class rather than one name at a time. 29 names moved, including `HARN_RELEASE_PIN_SHA`, `HARN_RELEASE_BASE`, `HARN_RELEASE_COST_LIMIT_USD`, `HARN_BUMP_FLEET_ENV_FILE`/`_ENV_FILES`, `HARN_ENV_VERBOSE`, and `HARN_SHIELDED_DIR`. Each was rejected by the pinned Harn before and is accepted now; `HARN_SHIELDED_DIR` in particular aborted `harn_shielded.sh`, which `exec`s the staged binary with the environment intact, so both of its documented invocations failed before the harness ran.

Three groups deliberately keep their existing names. Role prefixes such as `HARN_RELEASE` and `HARN_CHAT` are never set as bare variables — they compose into `HARN_RELEASE_PROVIDER`/`_MODEL`, which Harn's model-role grammar already accepts. `HARN_NO_VERIFY`, `HARN_INSTALL_ROOT`, and `HARN_INSTALL_FROM_SOURCE` belong to the public installer contract documented in Harn's own `install.sh`, and `scripts/install_harn.sh` already clears them with `env -u` before invoking `harn`. `HARN_REPO`, `HARN_STDIN`, and `HARN_TEST` are a Harn constant and two heredoc markers, not environment variables at all.
