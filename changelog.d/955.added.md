A failed hosted release run now leaves a typed receipt naming the precondition that failed and, when a re-dispatch is the right answer, the exact re-dispatch that would retry it. The run records the closed input set it was dispatched with, because the Actions API does not report it, and a terminal finalizer pairs that with the run's failing step. Which side of the release the step runs on is read from the workflow, from its position relative to the release harness, so a failure after the release may already be out is routed to recovery and never to a dispatch that would re-cut a published version. A failure the same inputs would repeat, and a step no registry row names, both escalate rather than defaulting to a retry. The finalizer fires on a cancelled or timed-out run as well as a failed one, because a release that ran out of its ceiling leaves the same question and used to leave no receipt.
